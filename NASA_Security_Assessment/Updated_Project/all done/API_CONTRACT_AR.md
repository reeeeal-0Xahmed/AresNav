# عقد الفرونت: كامل نطاق Jezero بشبكة 200م

الخريطة المعتمدة الآن `jezero-regional-200m`، وليست `jezero-3km`. حدود النقر هي حدود e في آخر رابط Mars Trek، نحو 70.49 ×59.59 كم. هذا عقد باك إند؛ لا توجد واجهة جديدة منشورة أو متصلة به بعد.

## تحميل بيانات المنطقة

```http
GET /mars/terrain/jezero-regional-200m
Accept: application/json
```

يرجع `map_id` و`version` و`width:353` و`height:298` و`cell_size_meters:200` و`grid`، ومعها `projection` و`affine` و`requested_bounds` و`raster_bounds` و`warnings` و`regional_scale:regional` و`source` و`thresholds` و`legend`.

خزّن version الناتج من GET واستخدمه في الطلب التالي باسم map_version. لا تنسخ قيمة إصدار ثابتة إلى كود الفرونت. للشبكة ترتيب صفوف من الشمال إلى الجنوب، و`grid[y][x]`، حيث x العمود من0 إلى352 وy الصف من0 إلى297.

الصورة أو raster الخاص بالشبكة يجب محاذاتها باستخدام raster_bounds لأن هناك padding متناظرًا أقل من خلية على الحواف. قيّد اختيارات المستخدم بrequested_bounds. تكبير الصورة على الشاشة لا يغير حجم خلية التخطيط ولا يضيف معلومات ارتفاعات دقيقة.

## إرسال نقطتين جغرافيتين — الأنسب لخريطة الموقع

```http
POST /mars/routes
Content-Type: application/json
Accept: application/json
X-CSRF-TOKEN: قيمة csrf_token من Laravel
```

Body مثال للاختبار فقط:

```json
{
  "map_id": "jezero-regional-200m",
  "map_version": "<version from terrain GET>",
  "start": {"lon": 77.0, "lat": 18.1},
  "target": {"lon": 77.9, "lat": 18.8}
}
```

النص بين <> مكان قيمة الإصدار، وليس قيمة مقبولة حرفيًا. يوجد مثال بقيمة فعلية في `tests/example_route_request.json`، لكن الفرونت الحقيقي يجب أن يقرأ أحدث version وأن يرسل نقاط المستخدم لا هذه الأرقام الثابتة.

لو مكتبة الفرونت ترجع `{lat,lng}`، حوّل lng إلى الحقل lon. أرسل قيم JSON كأرقام، لا نصوص. الإحداثيات مريخية: longitude شرقي وlatitude planetocentric، وليست مواقع على الأرض.

Laravel يفحص النقطتين ثم يحولهما إلى خلايا الشبكة، ويمنع اختيار خلية سالبة دون نقلها لأقرب مكان صالح. الاختيار الجغرافي يُسنَد طبيعيًا إلى الخلية التي تحتويه، والمسار يربط مراكز تلك الخلايا. تُحفظ النقاط الأصلية أيضًا حتى لا تضيع نقرة المستخدم.

## أو إرسال فهارس الخلايا

إذا الفرونت يعرض grid مباشرةً على Canvas، يمكن إرسال:

```json
{
  "map_id": "jezero-regional-200m",
  "map_version": "<version from terrain GET>",
  "start": {"x": 55, "y": 257},
  "target": {"x": 308, "y": 50}
}
```

لا تخلط `{x,y}` و`{lon,lat}` داخل نقطة، ولا تستخدم نوعًا مختلفًا للبداية والنهاية في نفس الطلب. لا ترسل grid أو width أو height من الفرونت؛ السيرفر يحمل الشبكة من ملفه المعتمد. x/y ليست بكسلات الشاشة.

عند تحويل نقرة Canvas استخدم نسبة موقعها داخل مستطيل العرض إلى width/height القادمين من GET، لا الرقم600 القديم. حافظ على نسبة353/298 إذا رسمت grid بأكملها؛ لا تقلب y مرة ثانية.

## استجابة النجاح

يرجع `status:success` و`request_id` و`map_id` و`map_version`. الحقلان `start` و`target` يحتويان فهارس الخلايا الصحيحة المستخدمة في C++، بينما `requested_start` و`requested_target` يحتويان اختيارات المستخدم الأصلية. `start_geographic` و`target_geographic` هما مركزا الخليتين بالـlon/lat.

`paths` يحتوي حتى ثلاثة مسارات مختلفة مرتبة حسب أقل تكلفة. كل عنصر يحتوي `rank` و`cost` و`steps` و`distance_meters` و`path` و`geographic_path` و`geojson`.

- path مصفوفة `{x,y}` للرسم على Canvas الخاصة بالشبكة.
- geographic_path مصفوفة `{lon,lat}` للرسم على خريطة المريخ.
- geojson لكل مسار Feature، وبنية geojson على مستوى الاستجابة FeatureCollection لجميع المسارات.

ترتيب المصفوفات الجغرافية داخل بنية GeoJSON هو `[lon,lat]`، وليس `[lat,lon]`. هذه البنية تحمل إحداثيات مريخية وليست WGS84 أرضية؛ استخدم طبقة وخريطة/CRS مناسبين للمريخ، ولا تستخدم مسافات أو خريطة أساس الأرض للحساب. بنيتها قابلة للرسم كـGeoJSON-style features؛ لا تعني تحويل المريخ إلى نظام WGS84 القياسي.

عندما البداية والنهاية في نفس الخلية، يوجد مسار واحد بتكلفة وطول صفر. هندسة GeoJSON تكون Point، لا LineString ذات نقطة واحدة غير صالحة. في المسارات المعتادة تكون LineString.

`path` على مستوى الاستجابة هو المسار الأول، للتوافق مع العقد السابق. قد تتعادل تكاليف أفضل ثلاثة مسارات أو تتجاور؛ اختلاف المسار لا يضمن فصلًا جغرافيًا كبيرًا. cost عقوبة عبور، وليس مسافة. distance_meters طول شبكي أفقي تقريبي، وليس طول السطح ثلاثي الأبعاد.

يوجد مثال كامل لنتيجة Laravel الفعلية في `tests/example_route_response.json`. لا ترسم نتيجة قديمة فوق نقاط جديدة عند تبديل اختيار المستخدم أثناء الانتظار؛ عطّل تغيير النقاط أثناء الطلب أو طابق request_id وrequested_start/target قبل الرسم.

## التخزين والجلسة

Laravel يحفظ `input_coordinates` الأصلية وstart_x/y وtarget_x/y ونسخة الخريطة قبل تشغيل C++، ثم يحفظ JSON النتيجة. الحصول على UUID يكون عند رجوع POST في التدفق المتزامن الحالي، لا في بداية Queue منفصلة.

```http
GET /mars/routes/{request_id}
Accept: application/json
```

هذا يرجع الطلب وinput_coordinates والنتيجة المحفوظة للجلسة التي أنشأته فقط. endpoints محملة من web.php مع جلسة وCSRF. أرسل cookies الجلسة وX-CSRF-TOKEN من نفس الموقع. إذا الفرونت على دومين مختلف نراجع CORS والمصادقة وSanctum قبل الدمج؛ لا تعطّل CSRF كحل سريع.

## التعامل مع الأخطاء

HTTP422 للحقول أو الحدود أو نقطة ممنوعة؛ أخطاء validation قد تكون message وerrors، وأخطاء العوائق تحتوي BLOCKED_POINT. HTTP409 مع MAP_CHANGED يعني أن الشبكة أو معلومات إحداثياتها تغيرت: أعد تحميل GET.

HTTP429 يعني ضغط طلبات أو PLANNER_BUSY؛ انتظر بدل تكرار الحساب سريعًا. HTTP504 مع PLANNER_TIMEOUT يعني أن الحساب لم يكتمل ضمن المهلة؛ لا توجد نتيجة مكتملة مضمونة. HTTP500/502 لمشكلة إعداد أو تشغيل أو بروتوكول البرنامج.

إذا لا يوجد مسار، قد يرجع HTTP200 لكن `status:error` و`error_code:NO_PATH` وpaths فارغة وبنية FeatureCollection فارغة. افحص status داخل JSON، لا HTTP200 وحده. لا تحذف العوائق لإجبار الخوارزمية على إيجاد طريق.

## الملفات التي نراجعها لاحقًا من الفرونت

أرسل مكوّن الخريطة والنقر، وملف fetch/Axios وعناوين API، وإعدادات CRS/طبقة المريخ، ومكوّن رسم النتيجة، وطريقة إدارة الجلسة والمصادقة. معها إطار الفرونت وإصدار Laravel وهل يعملان على نفس origin. عندها نراجع الربط الفعلي دون إعادة بناء خوارزمية المسارات من الصفر.
